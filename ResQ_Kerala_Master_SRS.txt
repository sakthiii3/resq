====================================================================== 1.
DOCUMENT PURPOSE
======================================================================

This document defines the complete software requirements for ResQ
Kerala, a technology-enabled emergency response platform for colleges,
festivals, public events, campuses, and other controlled large
gatherings.

The system enables participants and volunteers to report emergencies,
automatically capture location, classify and prioritize incidents,
identify appropriate responders, notify organizers/volunteers, track
response status, and maintain a complete incident history.

The SRS is intentionally implementation-oriented so that a student team
can use it as the master reference for UI design, database design, API
development, testing, deployment, demonstration, and final
documentation.

Core workflow:

REPORT -> LOCATE -> PRIORITIZE -> ASSIGN -> NOTIFY -> RESPOND -> RESOLVE

======================================================================
2. PROJECT VISION
======================================================================

Build a reliable emergency coordination system that reduces the time
between incident reporting and first response.

Primary value proposition:

“We don’t just report emergencies. We help the right responder reach the
incident quickly and give organizers visibility until resolution.”

The platform is not intended to replace professional emergency services,
police, fire, ambulance, hospital systems, or official government
emergency infrastructure. It is an event/campus coordination and
escalation system.

======================================================================
3. OBJECTIVES
======================================================================

3.1 Primary objectives

1.  Provide fast SOS and incident reporting.
2.  Capture incident type, description, evidence, and location.
3.  Automatically assign Low, Medium, or High priority.
4.  Identify appropriate available volunteers/organizers.
5.  Notify responders and organizers in near real time.
6.  Track incidents through Reported, Assigned, In Progress, and
    Resolved.
7.  Provide an organizer command dashboard.
8.  Show incidents on a map.
9.  Support nearest-volunteer identification.
10. Maintain an auditable incident history.
11. Detect probable duplicate reports.
12. Provide emergency contacts and escalation options.
13. Generate event-level analytics after incidents are resolved.

3.2 Secondary objectives

1.  Improve responder coordination.
2.  Reduce duplicate dispatches.
3.  Reduce manual communication overhead.
4.  Provide evidence for post-event review.
5.  Support multiple events/venues from one platform.
6.  Provide a clean, accessible mobile-first user experience.

5. TARGET USERS
======================================================================

5.1 Participant

A person attending the event/campus.

Capabilities: - View emergency information - Submit SOS - Submit
incident - Share location - Add description/photo - View own reports -
Receive status updates - Access emergency contacts

5.2 Volunteer / Responder

A trained or designated event responder.

Capabilities: - Set availability - Receive incident alerts - View
assigned incidents - Accept/decline assignment - Navigate to incident -
Update response status - Contact reporter when permitted - Mark incident
resolved - Add response notes

5.3 Organizer / Control Room Operator

Person responsible for event safety operations.

Capabilities: - Create/manage event - Monitor incidents -
Assign/reassign responders - Change priority - Escalate incidents - View
live map - Manage volunteers - Manage emergency contacts - Review
incident history - View analytics

5.4 Administrator

System-level manager.

Capabilities: - Manage organizations - Manage users/roles - Configure
incident categories - Configure priority rules - Configure event
settings - Manage system-level emergency contacts - Audit logs - Disable
accounts - Monitor system health

6. ASSUMPTIONS
======================================================================

1.  Users have a smartphone or web-capable device.
2.  GPS/location permission may be granted by users.
3.  Network connectivity is normally available.
4.  Event organizers register volunteers before the event.
5.  Volunteers have suitable permissions/training.
6.  Maps are provided by an external mapping service.
7.  Push notifications depend on device/network availability.
8.  The application may show approximate location when exact location is
    unavailable or when privacy settings require it.
9.  Emergency contact numbers are configured and verified by the
    organizer.
10. The platform is an event coordination tool and not an
    emergency-service replacement.

7. FUNCTIONAL REQUIREMENTS
======================================================================

FR-001 USER REGISTRATION

The system shall allow a user to register using: - Name - Mobile number
and/or email - Password or supported authentication method - Optional
organization/event code

The system shall validate required fields.

FR-002 LOGIN

The system shall allow authenticated users to sign in and sign out.

FR-003 ROLE MANAGEMENT

The system shall support: - PARTICIPANT - VOLUNTEER - ORGANIZER - ADMIN

A user shall only access functions allowed by the assigned role.

FR-004 EVENT CREATION

Organizer/Admin shall be able to create an event containing: - Event
name - Description - Venue - Start date/time - End date/time - Event
boundary/location - Emergency contacts - Status

FR-005 EVENT JOINING

Participants and volunteers shall be able to join an event using: -
Invitation - QR code - Event code - Organizer approval

FR-006 SOS REPORTING

The system shall provide a clearly visible SOS action.

When SOS is activated, the system shall: 1. Create an incident. 2.
Capture available location. 3. Set initial incident type to SOS/Unknown
if not specified. 4. Apply priority rules. 5. Notify the appropriate
control room/responders. 6. Display confirmation to the user. 7. Record
timestamp.

FR-007 INCIDENT REPORTING

A user shall be able to report: - Medical - Fire - Missing Person -
Crowd - Infrastructure - Electrical - Security - Other

The report shall support: - Incident type - Description - Location -
Number of affected people - Optional photo - Optional contact
preference - Optional urgency indicator

FR-008 LOCATION CAPTURE

The system shall support: - Current GPS location - Map pin selection -
Manual location description - Latitude - Longitude - Accuracy value
where available - Timestamp

If GPS fails, the user shall still be able to submit a report with a
manual location.

FR-009 LOCATION VALIDATION

The system shall determine whether the location is: - Inside event
boundary - Outside event boundary - Unknown

The organizer may configure whether outside-boundary incidents are
accepted.

FR-010 PRIORITY

The system shall support: - LOW - MEDIUM - HIGH

Priority shall be calculated using configurable rules.

Example scoring:

Severity: Low = 1 Medium = 2 High = 3

Affected people: 1 = 1 2-5 = 2 6+ = 3

Risk indicators: No immediate danger = 0 Potential danger = 1 Immediate
danger = 2

Suggested total: 1-3 = LOW 4-6 = MEDIUM 7+ = HIGH

The organizer shall be able to override priority with a recorded reason.

FR-011 INCIDENT STATUS

The system shall support: - REPORTED - ASSIGNED - IN_PROGRESS -
RESOLVED - CANCELLED

Optional: - ESCALATED - DUPLICATE

Every status change shall be timestamped and recorded.

FR-012 RESPONDER MATCHING

The system shall identify candidate volunteers using: 1. Availability 2.
Role/skill 3. Event membership 4. Distance 5. Current workload 6.
Optional category specialization

The system shall rank candidates.

Example ranking formula:

Responder Score = Distance Score * 0.45 + Availability Score * 0.25 +
Skill Match * 0.20 + Workload Score * 0.10

Weights shall be configurable.

FR-013 NEAREST VOLUNTEER

The system shall calculate approximate distance between incident and
responder.

The initial implementation may use the Haversine formula.

Distance: a = sin²((lat2-lat1)/2) + cos(lat1) * cos(lat2) *
sin²((lon2-lon1)/2) c = 2 * atan2(sqrt(a), sqrt(1-a)) distance =
EarthRadius * c

FR-014 ASSIGNMENT

Organizer shall be able to: - Assign responder - Reassign responder -
Cancel assignment - Escalate assignment

A responder shall be able to accept or decline an assignment.

FR-015 AUTO-ASSIGNMENT

For high-priority incidents, the system may automatically notify the
best-ranked responder.

If no responder accepts within a configurable timeout, the system
shall: 1. Notify the next candidate, or 2. Notify the organizer/control
room, or 3. Escalate according to event configuration.

FR-016 NOTIFICATIONS

The system shall support: - In-app notifications - Push notifications -
Optional SMS/email integration

Notification examples: - New high-priority incident - Assignment
received - Assignment accepted - Incident escalated - Incident resolved

FR-017 INCIDENT DASHBOARD

Organizer dashboard shall show: - Total incidents - High priority
count - Medium priority count - Low priority count - Reported count -
Assigned count - In-progress count - Resolved count - Unassigned count -
Average response time - Average resolution time

FR-018 MAP DASHBOARD

Organizer shall see incidents on a map.

Map features: - Incident markers - Priority indication - Incident type -
Responder location when sharing is active - Event boundary - Optional
heatmap - Marker clustering

FR-019 INCIDENT DETAILS

Incident detail page shall show: - Incident ID - Type - Description -
Priority - Status - Location - Reporter information according to privacy
rules - Assigned responder - Timeline - Attachments - Escalation
history - Resolution notes

FR-020 INCIDENT TIMELINE

The system shall record events such as: - Created - Location captured -
Priority changed - Assignment created - Assignment accepted - Responder
started - Escalated - Resolved - Cancelled

FR-021 RESOLUTION

Responder/Organizer shall be able to resolve an incident by entering: -
Resolution note - Optional category/result - Optional attachment -
Timestamp

FR-022 DUPLICATE DETECTION

The system shall identify possible duplicates using: - Same event -
Similar incident type - Distance threshold - Time window - Optional text
similarity

Example: Reports within 30 meters and 5 minutes with the same category
shall be flagged as possible duplicates.

The system shall not automatically delete duplicate reports.

FR-023 MERGE DUPLICATES

Organizer shall be able to: - Link reports - Select primary incident -
Mark another report as duplicate - Preserve original report records

FR-024 EMERGENCY CONTACTS

The system shall provide a dedicated emergency contacts screen.

Contacts may include: - Event control room - Medical team - Security -
Fire - Police - Ambulance - Venue management

Contacts shall be configured per event where appropriate.

FR-025 LIVE LOCATION SHARING

A volunteer may enable temporary live location sharing while responding.

The system shall: - Clearly indicate sharing status - Record start
time - Record stop time - Stop sharing when the response ends or user
disables it

Continuous participant tracking shall not be enabled by default.

FR-026 SEARCH

Organizer shall be able to search by: - Incident ID - Type - Status -
Priority - Reporter - Responder - Date/time

FR-027 FILTERING

Filters: - Priority - Status - Type - Assigned/unassigned - Location -
Time range

FR-028 ANALYTICS

System shall calculate: - Incident count by type - Incident count by
priority - Incident count by location - Response time - Resolution
time - Volunteer workload - Hourly incident distribution - Repeat-risk
locations

FR-029 EVENT HEATMAP

The system may generate a heatmap from incident locations.

The heatmap shall be informational and shall not be treated as a safety
prediction without sufficient data.

FR-030 AUDIT LOG

Security-sensitive actions shall be logged: - Login - Role change -
Incident creation - Priority override - Assignment - Reassignment -
Status change - Emergency contact modification - Account disablement

FR-031 DEMO MODE

The project shall support a demonstration mode with synthetic incidents,
locations, responders, and notifications.

Demo mode shall clearly identify simulated data.

8. NON-FUNCTIONAL REQUIREMENTS
======================================================================

NFR-001 PERFORMANCE

Normal API responses should target less than 2 seconds under the
expected student-project load, excluding external map/network
operations.

NFR-002 REAL-TIME RESPONSE

Incident and assignment updates should appear to connected users within
approximately 1-5 seconds under normal network conditions.

NFR-003 AVAILABILITY

The system should remain operational throughout the event period,
subject to hosting and network availability.

NFR-004 SCALABILITY

Initial target: - 1 event - 1,000 participants - 100 volunteers - 10
organizers - 10,000 incidents/events records

Architecture should permit future expansion.

NFR-005 SECURITY

Passwords shall never be stored as plaintext.

Authentication shall use secure tokens/session mechanisms.

Sensitive API endpoints shall require authentication and authorization.

NFR-006 AUTHORIZATION

Server-side authorization shall be enforced. Hiding UI controls shall
not be considered sufficient security.

NFR-007 PRIVACY

The system shall collect only information necessary for emergency
coordination.

Location shall be collected only when required or explicitly enabled.

Location sharing shall be visible to the user.

NFR-008 RELIABILITY

Incident creation should use an idempotency mechanism where possible so
repeated submissions do not create unintended duplicates.

NFR-009 USABILITY

SOS must be reachable quickly.

The reporting flow should require minimal typing.

The interface shall use readable labels and clear status indicators.

NFR-010 ACCESSIBILITY

The application should support: - Large touch targets - Keyboard
navigation where applicable - Sufficient text contrast -
Screen-reader-friendly labels - Clear error messages

NFR-011 MAINTAINABILITY

Code shall be organized into: - UI/presentation - API/service - data
access - business logic - notification - location/mapping

NFR-012 LOGGING

System errors shall be logged without unnecessarily exposing sensitive
personal information.

NFR-013 BACKUP

Database backups should be configured according to deployment
capability.

NFR-014 BROWSER SUPPORT

The web application should support current versions of major modern
browsers.

18. SOS UX
======================================================================

The SOS control shall: 1. Be clearly visible. 2. Require minimal
interaction. 3. Provide a confirmation step where practical to reduce
accidental triggers. 4. For an actual high-risk SOS, prioritize speed.
5. Immediately show that the request was received. 6. Display the
incident ID. 7. Show responder/control-room status when available.

Suggested screen:

EMERGENCY

[ HOLD TO SEND SOS ]

Location: Capturing… Status: Ready

After submission:

SOS SENT Incident: INC-1042 Priority: HIGH Location shared: YES
Responder: Being assigned

[CALL EMERGENCY CONTACT] [VIEW STATUS]

19. PRIORITY ENGINE
======================================================================

Priority must be deterministic and explainable.

Suggested rules:

HIGH: - Fire - Unconscious/unresponsive person - Severe medical
emergency - Multiple injured people - Active dangerous infrastructure -
Immediate crowd crush risk - Explicit SOS with critical indicators

MEDIUM: - Minor injury - Lost person - Significant crowding - Electrical
issue without immediate danger - Infrastructure issue affecting event
operations

LOW: - Lost item - Minor maintenance issue - Non-urgent request

The system should show a short explanation:

“High priority because: medical + 3 affected people.”

Organizer can override with reason.

======================================================================
20. RESPONDER MATCHING ALGORITHM
======================================================================

Input: - Incident coordinates - Incident type - Priority - Event -
Available responders

Filter: 1. Active user 2. Event member 3. Volunteer role 4. Available 5.
Suitable skill where configured

Rank: - Distance - Skill match - Current assignment count - Recent
workload - Availability

Example:

Candidate A: 150m, medical trained, 0 active tasks Candidate B: 90m, no
medical skill, 1 active task Candidate C: 300m, medical trained, 0
active tasks

The system may select A instead of simply choosing B.

This demonstrates “nearest suitable volunteer” rather than “nearest
user.”

======================================================================
21. DUPLICATE DETECTION
======================================================================

Initial rule:

If: same event AND same/similar incident type AND distance <= 30m AND
time difference <= 5 minutes

then flag as possible duplicate.

Optional text similarity can improve accuracy.

UI:

POSSIBLE DUPLICATE

Incident INC-100 Medical 2 minutes ago 25m away

Incident INC-101 Medical Now 18m away

[MERGE] [KEEP SEPARATE]

Never silently discard a user report.

======================================================================
22. ESCALATION LOGIC
======================================================================

Example:

T+0: Incident reported.

T+10 sec: High-priority notification sent.

T+60 sec: No responder accepted.

T+60 sec: Next suitable responder notified.

T+120 sec: Organizer alerted.

T+180 sec: Incident marked escalated.

Thresholds shall be configurable.

Do not claim that these timings guarantee real-world emergency response.

======================================================================
23. LOCATION PRIVACY
======================================================================

Rules: 1. Ask for location permission. 2. Explain why location is
required. 3. Do not continuously track participants by default. 4. Store
location only when necessary. 5. Volunteer live location is temporary.
6. Access to location is role-restricted. 7. Retention period should be
configurable. 8. Location should not be exposed publicly.

Suggested retention: - Active event: full operational data - Post-event:
organizer-configured retention - Old operational location data:
delete/anonymize where appropriate

======================================================================

2.  Password hashing.
3.  JWT/session expiration.
4.  Role-based authorization.
5.  Input validation.
6.  SQL injection prevention through parameterized queries/ORM.
7.  XSS protection.
8.  CSRF protection where applicable.
9.  Rate limiting for login/SOS APIs.
10. File type and file size validation.
11. Secure file storage.
12. Do not expose secrets in frontend code.

26. ERROR HANDLING
======================================================================

GPS unavailable: “Location could not be detected. Please choose your
location on the map.”

Network unavailable: “Connection unavailable. Your report will be
retried when possible.”

No responders: “No suitable responder is currently available. Control
room has been notified.”

Notification failure: “Incident created successfully. Notification
delivery is pending.”

Invalid attachment: “File type or size is not supported.”

Unauthorized: “You do not have permission to perform this action.”

27. OFFLINE/POOR NETWORK STRATEGY
======================================================================

For mobile/PWA implementation:

1.  Cache essential event configuration.
2.  Allow report drafting offline.
3.  Queue report submission.
4.  Retry when network returns.
5.  Prevent duplicate submission using client-generated request ID.
6.  Clearly show “Pending upload” state.

Do not claim real-time functionality while the device is offline.

35. DASHBOARD KPI DEFINITIONS

assignment.

responders, subject to the selected reporting definition.

40. AI POLICY FOR THE PROJECT
======================================================================

If AI is used, it should assist rather than replace emergency decision
making.

Acceptable student-project AI use: - Classify incident text into
categories - Summarize incident description - Detect similar incident
descriptions - Suggest priority for organizer review

AI output shall be clearly treated as a recommendation.

The final priority/dispatch decision should remain deterministic and/or
under authorized human control.

Avoid claiming that an AI model can diagnose medical conditions or
guarantee emergency outcomes.

41. DATA PRIVACY PRINCIPLES
======================================================================

Collect: - Minimum identity information - Incident information -
Necessary location - Necessary response information

Avoid collecting: - Unnecessary contacts - Continuous participant
movement - Unrelated personal information - Sensitive information not
needed for response

Users should be informed about: - What location is collected - Why it is
collected - Who can see it - How long it is retained - How sharing can
be stopped where applicable

For a real deployment in India, the team should obtain appropriate
legal, institutional, and privacy review before processing real
emergency data.

audit trail.

organizer override.
